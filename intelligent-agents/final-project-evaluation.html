Design Phase Reflection

WHAT

During the group design phase, I wrote the design decisions section and produced the sequence and activity diagrams. While reviewing a teammate’s class diagram, I noticed that human-review functions sat on the Orchestrator, but the researcher was absent from the static model despite appearing in the dynamic workflow.

SO WHAT

This exposed a weakness in the design itself: human oversight was central to our architecture, yet it was not represented consistently across views. Adding a boundary class improved that consistency, but the design was still unimplemented, so claims about bounded autonomy and reliable oversight remained assumptions rather than demonstrated behaviour.

NOW WHAT

In future, I will treat cross-diagram consistency as a design criterion and distinguish clearly between controls that are proposed and controls that have been tested.

Implemented Solution Reflection

WHAT

During implementation, review and testing exposed several controls and recorded states that were not operating as intended. In some cases the system still behaved correctly because the surrounding workflow happened to prevent the failure; in others, the run completed without making the underlying problem obvious.

Control Intended behaviour What actually happened Why it was easy to miss
Approval gate Retrieval should only proceed for researcher-approved sub-questions. Approval was recorded, but retrieval initially did not check it. The workflow normally called retrieval only after approval, so behaviour still appeared correct.
Retry limit retried_once should prevent another reformulation. The updated flag was written to a copy that did not reach the caller. Each sub-question was visited once per pass, so another retry was not normally attempted.
Retry and backoff Failed requests should be retried with exponential backoff. The decorator was attached to the wrong object, so requests were not retried. The code compiled and the full test suite still passed.
Query record If a reformulated query is worse, retain both the original papers and original query. The original papers were kept, but the reformulated query could still be recorded. The run completed normally; only the link between query and evidence was wrong.

SO WHAT

I learned that correct behaviour can occur for the wrong reason, and that a successful run does not prove its safeguards or records are trustworthy. None of these issues was exposed by an obvious failing test. They emerged through code review, inspecting logs and outputs, or when I tried to use the recorded retry state in the brief’s limitations.

NOW WHAT

I now test mechanisms directly: that a forbidden action does not occur, that a limit fires when reached, and that recorded state matches the evidence it describes. Testing outputs alone would have missed several of the failures above.
